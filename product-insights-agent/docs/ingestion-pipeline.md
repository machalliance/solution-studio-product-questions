# Ingestion Pipeline Guide

The ingestion pipeline processes product documentation PDFs into a MongoDB vector store, paired with an eval-driven grid sweep that gates chunk quality.

## End-to-End Flow

```
PDF → Gemini Markdown → Heading-based Chunking → Enrich Metadata → Contextualize → Embed → Store in MongoDB
                                                                                                  ↓
                                                Adjust Params ← Below Threshold? ← Judge Quality ← Eval Loop
```

### Step 1: PDF-to-Markdown Extraction

`pipeline/extract-markdown.ts`

The pipeline sends the product manual PDF to Gemini 3 Pro Preview via the Vercel AI Gateway (`"google/gemini-3-pro-preview"`). Gemini converts the PDF to well-structured Markdown, preserving headings, tables, lists, and formatting. Multi-language content is handled by the extraction prompt — only English content is extracted.

The Markdown result is cached to `data/markdown/{productId}.md`. Subsequent runs use the cache unless `--force` is passed.

### Step 2: Heading-Based Chunking

`pipeline/chunk.ts`

The Markdown is chunked in two phases:

1. **Heading split**: Split on Markdown headings (`#`, `##`, `###`) — each heading becomes a section boundary with heading metadata attached automatically.
2. **Recursive character split**: Sections exceeding the target size are sub-split on paragraph/sentence boundaries.

| Parameter       | Default                        | Description                                     |
| --------------- | ------------------------------ | ----------------------------------------------- |
| `chunkSize`     | 512 tokens                     | Target chunk size (cl100k_base)                 |
| `overlap`       | 50 tokens                      | Overlap between adjacent chunks                 |
| `minChunkSize`  | 50 tokens                      | Chunks below this are merged with neighbors     |
| `splitPatterns` | paragraph → heading → sentence | Ordered preference for natural split boundaries |

Sizes are measured in **tokens**, not characters. Token counts use the `cl100k_base` encoding via `js-tiktoken` (the encoding used by `text-embedding-3-small`, `gpt-4o`, and `gpt-5-mini`). Character counts drift 2–3× on tables, CJK, and code fences; token counts stay stable.

No hardcoded section headers or product-specific configuration is needed — the pipeline generalizes to any product manual.

### Step 3b: Contextual Retrieval

`pipeline/contextualize.ts`

Before embedding, each chunk is augmented with a **1–2 sentence context header** generated by Claude Sonnet 4.5. The prompt includes the full document and the chunk, and asks the model to situate the chunk globally. The resulting context is prepended to the chunk before embedding:

```
embedding input = "{context}\n\n{chunk body}"
```

The raw chunk body is still what the runtime LLM answerer sees — context headers only influence retrieval, never generation.

**Why this matters.** Anthropic's [Contextual Retrieval](https://www.anthropic.com/news/contextual-retrieval) benchmark showed a 35% reduction in retrieval failures vs. raw chunks (49% combined with BM25 + rerank). The practical effect for shoppers: a question like "how do I empty it?" resolves to the right chunk even when the chunk doesn't contain the product name or the word "dustbin" — the context header fills that gap.

**Prompt caching.** The full Markdown document is identical across all N chunk requests, so we mark that portion of the user prompt with `cacheControl: ephemeral`. Anthropic caches the prefix and reuses it across sibling requests, turning N×document into 1×document + N×chunk. Without caching, per-chunk contextualization would cost ~100× more.

### Step 3: Metadata Enrichment

`pipeline/metadata.ts`

Each chunk is enriched with:

- **Section header**: detected from the PDF structure (e.g., "Safety Information", "How to Use")
- **Page numbers**: which pages the chunk spans
- **Topic category**: classified by keyword detection into one of: safety, setup, usage, maintenance, troubleshooting, specifications, package-contents, general

### Step 4: Embedding and Storage

`lib/db/vectors.ts`

Chunks are embedded using OpenAI `text-embedding-3-small` (1536 dimensions) via the Vercel AI SDK `embedMany()` function. Embedded chunks are stored in the `chunks` collection in MongoDB with the document structure:

```json
{
  "text": "chunk text content",
  "context": "This section of the Dreame X40 Ultra manual describes day-to-day operation.",
  "embedding": [0.123, -0.456, ...],  // 1536 floats — computed from context + text
  "productId": "dreame-x40-ultra",
  "metadata": {
    "sectionHeader": "How to Use",
    "pageNumbers": [12, 13],
    "chunkIndex": 7,
    "charCount": 1834,
    "tokenCount": 456
  }
}
```

The `context` field is persisted for debugging and observability but is never returned to the runtime answer path — `similaritySearch` only projects the raw `text`.

A vector search index is created on the `embedding` field with cosine similarity.

### Step 5: Eval-Driven Grid Sweep (Optional)

`pipeline/feedback-loop.ts`

When run as a sweep, the pipeline:

1. **Generates a golden eval set** (`pipeline/eval-set.ts`): an LLM reads the full PDF and produces 25 golden Q&A pairs with expected source passages. The eval set is cached to disk and reused across runs. 25 is the demo-appropriate size; see `docs/production-scaling/ingestion.md` for why production teams scale to 50–100 SME-curated goldens.

2. **Judges retrieval quality** (`pipeline/judge.ts`): for each golden Q&A, the pipeline runs a vector search, then three per-metric LLM judges score the results on the three [RAGAS](https://docs.ragas.io/en/stable/) (Retrieval-Augmented Generation Assessment) retrieval metrics:
   - **Faithfulness** (0-1): are the retrieved chunks relevant to the question's topic?
   - **Context Recall** (0-1): what fraction of expected claims are covered by retrieved chunks? (Claim-level attribution)
   - **Context Precision** (0-1): are the most relevant chunks ranked highest? (Weighted precision@k)

   Plus secondary deterministic scores for chunk quality:
   - **Chunk size distribution**: coefficient of variation of chunk lengths
   - **Deduplication**: near-duplicate detection via Jaccard similarity
   - **Metadata completeness**: percentage of chunks with complete metadata
   - **Section coverage**: fraction of questions with at least one chunk from an expected section
   - **Sentence completeness**: fraction of chunks that start/end on clean boundaries
   - **Structural integrity**: fraction of chunks with intact tables and lists

   > **Why no coherence metric?** No major eval framework (RAGAS, DeepEval, TruLens, Evidently AI) evaluates coherence on retrieved context — it is universally a generation-quality metric. Raw top-K retrieval from different document sections is expected to be disjointed; the agent/LLM synthesis is what produces a coherent answer. Chunk-level quality is measured by the deterministic secondary scores instead.

3. **Sweeps a fixed grid** of chunking configs (`chunkSize ∈ {256, 512, 1024}` × `overlap ∈ {0, 50, 100}` — 9 cells), re-chunking and re-evaluating for each.

4. **Prints a scorecard** across all 9 cells and surfaces the highest-scoring one as a suggested winner. A human reads the table, picks a config, and freezes it in `DEFAULT_CHUNK_CONFIG`.

5. **Saves an eval report** per cell as a timestamped JSON file in `data/eval-reports/`.

The sweep replaced an earlier convergence-style tuner that iteratively nudged `chunkSize` / `overlap` against the weakest metric until scores cleared a threshold. That approach is a demo-ism — it uses the fixed golden set as a training signal, and the greedy walk can get stuck in a local optimum and never visit the true best config. The sweep is run once during pipeline design and frozen; see `docs/production-scaling/ingestion.md` § "Eval scaling" for why re-running it on a schedule conflates calibration with ingestion.

## Golden Eval Set

`data/eval-sets/dreame-x40-ultra.json`

The golden eval set is the ground truth for measuring retrieval quality. It contains 25 question-answer pairs generated by an LLM from the full product Markdown, each with:

- **Question**: a natural question a shopper would ask (e.g., "Can I use the robot near my bathroom?")
- **Expected answer**: the correct answer derived from the manual
- **Source passage**: the verbatim text from the manual that supports the answer
- **Topic**: category tag (safety, setup, usage, maintenance, troubleshooting, specifications, package-contents)
- **Claims**: atomic factual claims the answer contains — used for Context Recall scoring (claim-level attribution)
- **Relevant sections**: Markdown heading texts from the source that contain relevant information — used for section coverage scoring

The eval set is cached to disk and committed to git. It is only regenerated when explicitly requested (`--regenerate-eval-set` flag). This ensures eval scores are comparable across runs — the same questions are asked every time.

Topics are distributed across the manual's content areas to ensure broad coverage:

| Topic            | Count |
| ---------------- | ----- |
| usage            | 4     |
| maintenance      | 4     |
| specifications   | 3     |
| package-contents | 2     |
| safety           | 2     |
| troubleshooting  | 2     |
| setup            | 1     |

## Eval Reports and History

`data/eval-reports/`

Every eval run produces a timestamped JSON report committed to git, so you can track quality over time. Each report contains:

- **Overall score** and **pass/fail** against configurable thresholds
- **Dimension averages**: faithfulness, context recall, context precision
- **Secondary scores**: chunk size distribution, deduplication, metadata quality, section coverage, sentence completeness, structural integrity
- **Per-question results**: individual scores, LLM judge reasoning, and per-claim attribution breakdowns for each golden Q&A pair

### Viewing eval history

```bash
# Summary table — shows scores and deltas across all runs
pnpm eval:history

# Per-question breakdown for the latest run
pnpm eval:history -- --detail

# Show only the last N runs
pnpm eval:history -- --last 3
```

This is a local alternative to tools like LangSmith for tracking eval quality. The eval reports are committed to git so the team can see how pipeline changes (chunking params, embedding model, etc.) affect retrieval quality over time.

### Current thresholds

| Threshold   | Value | Description                                     |
| ----------- | ----- | ----------------------------------------------- |
| perQuestion | 0.5   | Minimum average score for a single Q&A pair     |
| overall     | 0.65  | Minimum average score across all Q&A pairs      |
| passRate    | 80%   | Minimum fraction of questions above perQuestion |

## Running the Pipeline

### Prerequisites

```bash
# Start MongoDB (uses mongodb-atlas-local for vector search support)
docker-compose up -d

# Ensure .env.local has:
#   MONGODB_URI=mongodb://localhost:27017/product-insights?directConnection=true
#   AI_GATEWAY_API_KEY=...  (routes chat models and embeddings)
```

### Commands

```bash
# Basic ingestion (extract → chunk → embed → store)
pnpm pipeline:ingest --verbose

# With verification queries against the vector store
pnpm pipeline:ingest --verify

# Run eval using Claude CLI (uses your Claude Code subscription, no ANTHROPIC_API_KEY needed)
pnpm eval:via-claude

# Regenerate the golden eval set from scratch
pnpm eval:via-claude --regenerate-eval-set

# Run eval using direct Anthropic API (requires ANTHROPIC_API_KEY)
pnpm eval:ingestion

# View eval history
pnpm eval:history
pnpm eval:history -- --detail
```

### Typical workflow

1. Make a pipeline change (chunking params, embedding model, metadata enrichment, etc.)
2. Re-ingest: `pnpm pipeline:ingest --verbose`
3. Re-eval: `pnpm eval:via-claude`
4. Compare: `pnpm eval:history` — look for score improvements/regressions
5. Commit the new eval report to git

## Multi-Language Handling

The Dreame X40 Ultra manual contains content in English, German, French, and Italian. The Gemini extraction prompt instructs the model to extract only English content. Non-English sections are excluded from the Markdown output, preventing retrieval of foreign-language chunks.

## Adding a New Product

1. Place the product PDF in `data/`
2. Create a product JSON file in `data/products/your-product.json` matching the `ProductData` interface:
   ```json
   {
     "id": "your-product-id",
     "name": "Product Name",
     "brand": "Brand",
     "price": 999.99,
     "currency": "CAD",
     "description": "...",
     "features": ["..."],
     "specifications": { "key": "value" }
   }
   ```
3. Run ingestion: `pnpm pipeline:ingest` — no product-specific configuration needed. The pipeline extracts Markdown via Gemini, chunks on headings, and classifies topics automatically.
4. Run the eval suite to validate: `pnpm eval:ingestion`

## Troubleshooting

**"MongoDB connection failed"** / **"getaddrinfo ENOTFOUND"**: The `mongodb-atlas-local` Docker image uses a replica set with an internal hostname. Add `?directConnection=true` to your `MONGODB_URI` in `.env.local`:

```
MONGODB_URI=mongodb://localhost:27017/product-insights?directConnection=true
```

Also ensure Docker is running and `docker-compose up -d` has been executed.

**"Eval loop did not converge"**: The eval report in `data/eval-reports/` shows per-dimension scores. If faithfulness is low, chunks may be too large — try decreasing `chunkSize`. If context recall is low, increase `overlap` for better boundary coverage. If context precision is low, decrease `chunkSize` for more precise matching.

**"AI Gateway authentication failed"**: Embeddings and chat models both route through the Vercel AI Gateway. Ensure `AI_GATEWAY_API_KEY` is set in `.env.local` and that `src/server/db/vectors.ts` uses the gateway model string `"openai/text-embedding-3-small"` (not a direct provider import).

**"Embedding API rate limit"**: The pipeline embeds all chunks in a single `embedMany()` call. For very large documents, you may need to batch the embedding step.
